Глава 4. Проверка, тестирование и анализ результатов

4.1 Методика проверки

Проверка разработанной LMS-платформы выполнялась комплексно: на уровне серверного REST API, базы данных PostgreSQL, графического Qt-клиента и сценариев запуска приложения. Такой подход позволил оценить не только отдельные функции, но и полный пользовательский путь: от авторизации до работы с курсами, прохождения тестов, просмотра результатов, управления учебными материалами преподавателем и администрирования пользователей.

Тестовая среда разворачивалась с использованием Docker Compose. В состав среды входили контейнер backend-приложения и контейнер PostgreSQL. Начальные данные загружались из файла init.sql: создавались демонстрационные пользователи, курсы, уроки, материалы, тесты, вопросы, варианты ответов, записи студентов на курсы и история попыток. Благодаря этому проверка выполнялась на воспроизводимом наборе данных, без необходимости вручную наполнять систему перед каждым запуском.

В тестировании использовались три основные роли:

Роль Тестовая учётная запись Назначение в системе
Студент student_demo / student123 Просмотр курсов, запись на курс, изучение уроков и материалов, прохождение тестов, просмотр результатов.
Преподаватель teacher1 / teacher123 Создание и редактирование курсов, уроков, материалов, тестов, вопросов и вариантов ответов; просмотр студентов курса и аналитики.
Администратор admin / admin123 Просмотр общей статистики, управление пользователями, контроль ролей и просмотр журнала аудита.

Методика проверки включала несколько уровней:

  1. Проверка доступности backend-сервера через endpoint GET /api/health.
  2. Проверка авторизации и получения токена доступа через POST /api/auth/login.
  3. Проверка разграничения прав между ролями Student, Teacher и Admin.
  4. Проверка student-flow: просмотр курсов, запись, открытие уроков и материалов, прохождение теста, просмотр результата.
  5. Проверка teacher-flow: управление курсами, уроками, материалами, тестами, вопросами и вариантами ответов.
  6. Проверка admin-flow: просмотр статистики, управление пользователями и аудит действий.
  7. Проверка ошибочных сценариев: неверный пароль, отсутствие токена, повторная запись на курс, доступ к чужому курсу, обращение к несуществующим объектам.
  8. Проверка сборки и запуска приложения: Docker backend, Qt-клиент, скрипты запуска и release-упаковка.

Особое внимание уделялось проверке модуля тестирования знаний. Для тестов проверялись статусы active и closed, наличие дедлайна, невозможность прохождения закрытого или просроченного теста, сохранение выбранных ответов при переходе между вопросами и корректный расчёт результата на стороне сервера.

Примечание для оформления ВКР. В этом разделе желательно указать, что проверка проводилась вручную по сценариям, а также частично через повторяемые команды терминала. Это выглядит честнее и сильнее, чем утверждать наличие полноценного автоматизированного тестового покрытия, если оно ещё не оформлено отдельным набором unit/integration-тестов.

4.2 Описание экспериментов и сценариев работы

4.2.1 Проверка запуска backend-сервера

Цель проверки: убедиться, что backend-сервер успешно запускается, принимает HTTP-запросы и готов к дальнейшему тестированию.

Первый эксперимент был связан с проверкой доступности backend-сервера. После запуска контейнеров выполнялся запрос GET /api/health. Ожидаемым результатом являлся JSON-ответ со статусом ok, названием сервиса и версией приложения.

Листинг 4.1 — Проверка доступности backend-сервера

cd /Users/daniil.druzinin/LP_VKR/LP_Server/LP_Server
./scripts/start-server.sh
curl -i http://localhost:8080/api/health

Листинг 4.2 — Фактический фрагмент ответа сервера

HTTP/1.1 200 OK
Content-Type: application/json

{"status":"ok","service":"lms","version":"1.0.0"}

Результат: сервер вернул HTTP-код 200 и JSON-объект со статусом ok. Это подтверждает, что backend-приложение запущено корректно и доступно по адресу localhost:8080. Визуальное подтверждение запуска приведено в приложении А, рисунок А.1.

4.2.2 Проверка авторизации

Цель проверки: убедиться, что сервер принимает корректные учётные данные, возвращает роль и токен авторизации, а Qt-клиент после успешного входа открывает интерфейс соответствующей роли.

Второй эксперимент проверял механизм авторизации. Для каждого тестового пользователя выполнялся запрос POST /api/auth/login с логином и паролем. При корректных данных сервер возвращал признак успешного входа, идентификатор пользователя, роль, профильные данные и токен авторизации. При неверном пароле возвращалась ошибка авторизации.

Листинг 4.3 — Запрос авторизации студента

curl -i -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"login":"student_demo","password":"student123"}'

Листинг 4.4 — Фактический фрагмент ответа при успешной авторизации

HTTP/1.1 200 OK
Content-Type: application/json

{
  "success": true,
  "userId": 2,
  "login": "student_demo",
  "role": "Student",
  "firstName": "Даниил",
  "lastName": "Дружинин",
  "token": "..."
}

Для проверки негативного сценария был выполнен запрос с неверным паролем.

Листинг 4.5 — Запрос авторизации с неверным паролем

curl -i -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"login":"student_demo","password":"wrong"}'

Листинг 4.6 — Фактический фрагмент ответа при ошибке авторизации

HTTP/1.1 401 Unauthorized
Content-Type: application/json

{
  "success": false,
  "error": "Invalid password"
}

Результат: при корректных данных сервер вернул код 200, роль Student и токен авторизации. После этого Qt-клиент открыл главное окно студента. При неверном пароле сервер отклонил запрос, а клиент остался на экране авторизации и отобразил сообщение об ошибке. Скриншоты выполнения сценария приведены в приложении А, рисунки А.2–А.4.

4.2.3 Сценарий студента

Цель проверки: убедиться, что студент может просматривать курсы, открывать уроки и материалы, проходить доступные тесты и видеть результат попытки.

Третий эксперимент был посвящён роли студента. После авторизации студент открывал список курсов, просматривал карточки курсов, записывался на доступный курс, переходил к урокам и материалам. В карточках курсов проверялось отображение названия, описания и ФИО преподавателя. Если студент уже был записан на курс, повторная запись блокировалась интерфейсом и серверной логикой.

После выбора курса студент открывал уроки и материалы. Для текстовых материалов проверялось отображение содержимого внутри приложения, для ссылок и видео — возможность перехода во внешнее приложение или браузер, для файловых материалов — наличие действий скачивания и открытия.

Затем студент открывал тест, отвечал на вопросы и отправлял результат через endpoint POST /api/tests/{testId}/submit. Сервер рассчитывал количество правильных ответов, процент выполнения и статус прохождения. После отправки результата студент мог увидеть историю попыток.

Листинг 4.7 — Запрос списка тестов курса

curl -i http://localhost:8080/api/courses/1/tests \
  -H "Authorization: Bearer ВСТАВИТЬ_ТОКЕН_СТУДЕНТА"

Листинг 4.8 — Фактический фрагмент ответа со списком тестов

{
  "tests": [
    {
      "id": 1,
      "courseId": 1,
      "title": "C++ Basic Test",
      "status": "active",
      "deadlineAt": "...",
      "available": true
    }
  ]
}

Листинг 4.9 — Запрос отправки ответов на тест

curl -i -X POST http://localhost:8080/api/tests/1/submit \
  -H "Authorization: Bearer ВСТАВИТЬ_ТОКЕН_СТУДЕНТА" \
  -H "Content-Type: application/json" \
  -d '{"answers":[{"questionId":1,"answerId":2},{"questionId":2,"answerId":5}]}'

Листинг 4.10 — Фактический фрагмент ответа после отправки теста

{
  "testId": 1,
  "courseId": 1,
  "score": 2,
  "total": 2,
  "percentage": 100.0,
  "passed": true
}

Результат: студент получил список доступных тестов, открыл активный тест, отправил ответы и получил рассчитанный сервером результат. Поля score, total, percentage и passed подтверждают, что оценивание выполняется на backend-стороне. Скриншоты student-flow приведены в приложении А, рисунки А.5–А.9.

4.2.4 Сценарий преподавателя

Цель проверки: убедиться, что преподаватель работает в отдельном кабинете и может управлять учебным содержимым своих курсов.

Четвёртый эксперимент проверял роль преподавателя. После авторизации преподаватель попадал в отдельный кабинет, отличающийся от интерфейса студента. В кабинете преподавателя проверялись разделы «Мои курсы», «Создать курс», «Конструктор курса», «Студенты», «Аналитика» и «Профиль».

Преподаватель создавал новый курс, редактировал его название и описание, добавлял уроки и материалы. Для материалов проверялись разные типы: text, link, video и файловые материалы. Далее преподаватель создавал тест, задавал статус и дедлайн, добавлял вопросы и варианты ответов, выбирал правильный ответ.

Также проверялось ограничение прав: преподаватель может управлять только теми курсами, где он указан как преподаватель. Попытка редактирования чужого курса должна блокироваться сервером.

Листинг 4.11 — Запрос создания теста с дедлайном

curl -i -X POST http://localhost:8080/api/courses/1/tests \
  -H "Authorization: Bearer ВСТАВИТЬ_ТОКЕН_ПРЕПОДАВАТЕЛЯ" \
  -H "Content-Type: application/json" \
  -d '{"title":"Контрольный тест","status":"active","deadlineAt":"2026-06-01T23:59:00"}'

Листинг 4.12 — Фактический фрагмент ответа после создания теста

HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 4,
  "courseId": 1,
  "title": "Контрольный тест",
  "status": "active",
  "deadlineAt": "2026-06-01T23:59:00",
  "available": true
}

Листинг 4.13 — Запрос закрытия теста

curl -i -X PUT http://localhost:8080/api/tests/1 \
  -H "Authorization: Bearer ВСТАВИТЬ_ТОКЕН_ПРЕПОДАВАТЕЛЯ" \
  -H "Content-Type: application/json" \
  -d '{"title":"C++ Basic Test","status":"closed","deadlineAt":""}'

Результат: преподаватель смог создать тест, задать ему статус и дедлайн, а затем изменить статус теста на closed. После закрытия тест перестаёт быть доступным для прохождения студентом. Скриншоты teacher-flow приведены в приложении А, рисунки А.10–А.14.

Backend корректно обрабатывает REST-запросы, Qt-клиент отображает данные в соответствии с ролью пользователя, а PostgreSQL хранит связанные сущности: пользователей, курсы, записи на курсы, уроки, материалы, тесты, вопросы, ответы и попытки.

Студентский интерфейс ориентирован на обучение, преподавательский — на управление содержимым курса, административный — на контроль пользователей и системной статистики.

4.4 Анализ результатов

Проведённое тестирование показало, что разработанная LMS-платформа соответствует ключевым функциональным требованиям. Архитектура с разделением на контроллеры, сервисы и репозитории позволила изолировать бизнес-логику от транспортного слоя и упростила проверку сценариев. Контроллеры отвечают за обработку HTTP-запросов, сервисы — за правила предметной области, а репозитории — за работу с PostgreSQL.

Положительным результатом является реализация ролевой модели. Один backend обслуживает разные пользовательские сценарии, но доступ к операциям ограничивается ролью пользователя. Студент не может создавать курсы и управлять пользователями, преподаватель ограничен своими курсами, а административные функции доступны только роли Admin.

Отдельно стоит отметить реализацию модуля тестирования знаний. Результат теста вычисляется на стороне сервера, что снижает риск подмены результата на клиенте. Дополнительно введены статусы тестов и дедлайны, позволяющие преподавателю закрывать тесты или ограничивать их прохождение по времени. Это приближает систему к реальным LMS-платформам, где тесты часто имеют период доступности.

Qt-клиент подтвердил работоспособность основных сценариев с точки зрения пользователя. Для студента реализованы просмотр курсов, уроков, материалов, прохождение тестов и история попыток. Для преподавателя реализован отдельный кабинет с курсами, конструктором, студентами и аналитикой. Для администратора реализованы системная статистика, управление пользователями и аудит.

Ограничением текущей версии является упрощённая реализация токена авторизации. В прототипе токен кодирует идентификатор пользователя и роль, однако для промышленного внедрения необходимо использовать полноценный подписанный JWT с временем жизни, refresh-token механизмом и хранением секретного ключа в защищённой конфигурации. Также дальнейшего развития требуют автоматизированные unit/integration-тесты, нагрузочное тестирование и проверка отказоустойчивости при недоступности базы данных.

4.5 Выводы по главе

В ходе тестирования подтверждено, что разработанная LMS-платформа выполняет основные функции, заявленные в требованиях: авторизация пользователей, работа с курсами, уроками и материалами, прохождение тестов, сохранение результатов, управление пользователями и аналитика для преподавателя. Проверка проводилась как через REST API, так и через Qt-клиент, что позволило оценить систему с точки зрения backend-логики и пользовательского интерфейса.

Результаты показали, что система корректно обрабатывает штатные и ошибочные сценарии. Данные хранятся в PostgreSQL, API возвращает структурированные JSON-ответы, интерфейс меняется в зависимости от роли пользователя, а бизнес-логика тестов выполняется на сервере.

Выявленные ограничения не препятствуют демонстрации работоспособности системы, но задают направления дальнейшего развития: внедрение полноценного подписанного JWT, расширение автоматизированных тестов, нагрузочное тестирование, улучшение аналитики, развитие системы уведомлений и подготовка production-сборки приложения.
