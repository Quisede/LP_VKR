Вариант для второй главы

2.4 Ролевая модель и функциональные подсистемы платформы

Одним из основных проектных решений является разделение системы по ролям пользователей. В платформе выделяются студент, преподаватель и администратор. Такое разграничение определяет не только состав доступных экранов, но и набор операций, которые пользователь может выполнять на серверной стороне. Студент работает с доступными курсами, изучает уроки и материалы, проходит тесты и просматривает собственные результаты. Преподаватель отвечает за наполнение курсов, создание учебных материалов и тестов, а также за просмотр результатов обучающихся. Администратор управляет пользователями, ролями и общим состоянием системы.

Подсистема аутентификации обеспечивает вход пользователя в систему и определение его роли. После успешной проверки учётных данных последующие действия пользователя выполняются с учётом его полномочий. Проверка доступа должна выполняться централизованно на стороне сервера, поскольку ограничение только на уровне интерфейса не гарантирует защиты данных. Например, студент не должен получать доступ к административным функциям, преподаватель должен работать только со своими курсами, а просмотр результатов должен ограничиваться правами конкретной роли.

Основной единицей организации обучения в системе является курс. Курс объединяет уроки, материалы и тесты, а также связывается с преподавателем и записанными студентами. На проектном уровне система должна поддерживать создание и изменение курсов, добавление учебного контента, запись студентов и получение сведений об участниках. Для учебных материалов предусматриваются разные типы содержимого: текстовые материалы, ссылки, видео и файлы. Это позволяет использовать платформу не только для хранения простых текстов, но и для более близкой к реальной LMS организации учебного контента.

Подсистема тестирования предназначена для формализованной проверки знаний. Тест связан с курсом и включает вопросы с вариантами ответов. При прохождении теста студент получает только текст вопроса и варианты ответа, без информации о правильном варианте. Проверка результата выполняется на серверной стороне, где хранятся правильные ответы. После отправки ответов система формирует попытку прохождения, сохраняет результат и делает его доступным в соответствии с ролью пользователя: студенту — для просмотра собственной истории, преподавателю — для анализа результатов по своим курсам, администратору — в рамках расширенного контроля системы.

Таким образом, функциональные подсистемы платформы связаны между собой через ролевую модель. Аутентификация определяет пользователя и его права, подсистема курсов задаёт структуру обучения, учебные материалы наполняют курс содержанием, а тестирование фиксирует результаты освоения материала. Такое объединение позволяет рассматривать платформу не как набор отдельных функций, а как целостную систему сопровождения учебного процесса.

2.5 Организация клиентского модуля

Клиентская часть проектируется как настольное приложение, через которое пользователь выполняет основные действия в системе. В интерфейсе должны быть разделены сценарии для разных ролей: студенту доступны курсы, уроки, материалы, тесты и результаты; преподавателю — управление курсами, учебным содержанием, студентами и аналитикой; администратору — управление пользователями и системными данными. Такое разделение делает интерфейс понятнее и уменьшает риск случайного доступа пользователя к неподходящим функциям.

На проектном уровне клиентский модуль целесообразно разделить на визуальные страницы, модели данных и сетевой слой. Визуальные страницы отвечают за отображение информации и обработку действий пользователя. Модели данных позволяют представить курс, урок, материал, тест, вопрос и результат как отдельные сущности клиента. Сетевой слой отделяет интерфейс от деталей HTTP-взаимодействия с сервером. Благодаря этому изменение структуры API или формата ответа не должно требовать переработки каждой страницы приложения.

Во второй главе важно зафиксировать именно архитектурный принцип организации клиента. Конкретные классы Qt, структура окон, использование сетевого менеджера, обработка JSON-ответов и наполнение интерфейса данными относятся к программной реализации и рассматриваются в третьей главе.

2.6 Проектирование хранения данных

Для хранения данных платформы используется реляционная модель. Такой подход подходит для LMS, поскольку предметная область состоит из связанных сущностей: пользователей, курсов, записей на курсы, уроков, материалов, тестов, вопросов, вариантов ответов и попыток прохождения. Связи между этими сущностями должны быть явно зафиксированы, чтобы система могла поддерживать целостность данных.

Пользователь связан с ролью и выполняемыми действиями. Курс связан с преподавателем, уроками, материалами, тестами и записанными студентами. Тест связан с вопросами, вопросы — с вариантами ответов, а попытка прохождения связывает конкретного пользователя с конкретным тестом и рассчитанным результатом. Для предотвращения несогласованных данных в модели предусматриваются первичные и внешние ключи, ограничения уникальности и каскадное удаление зависимых записей.

Репозиторный слой в проектной модели отделяет бизнес-логику от конкретного способа хранения данных. Сервисы работают с операциями предметной области, такими как получение пользователя, загрузка курса, сохранение записи на курс или сохранение результата тестирования, а не с деталями SQL-запросов. Физическая структура таблиц, поля, SQL-скрипты и подключение к PostgreSQL раскрываются в главе программной реализации.

В подразделе «Реализация серверной части»

После объединения 2.4–2.8 во второй главе третья глава должна подробнее показать, как эти подсистемы реализованы на сервере. Можно добавить или усилить следующий фрагмент:

Ролевая модель, описанная в проектной главе, реализована на серверной стороне через проверку текущего пользователя и его роли при обработке защищённых маршрутов. Контроллер принимает HTTP-запрос и извлекает данные авторизации, после чего передаёт управление сервисному слою. Именно сервисный слой принимает решение о допустимости операции: студент может работать только со своими учебными данными, преподаватель — со своими курсами, а административные функции доступны только роли Admin.
Для курсов, уроков и материалов серверная часть реализует набор операций создания, чтения, изменения и удаления. CourseService проверяет корректность данных курса, права преподавателя на изменение курса, возможность записи студента и отсутствие повторной записи. LessonService и MaterialService отвечают за работу с учебным содержимым и проверяют, имеет ли пользователь доступ к соответствующему курсу. Такой подход позволяет выполнять контроль не только в интерфейсе, но и на уровне backend-логики.
Модуль тестирования реализован через контроллеры тестов, вопросов и попыток прохождения. Для студента вопросы возвращаются без признака правильного ответа. Для преподавателя и администратора предусмотрен режим управления тестом, где доступна полная структура вопроса. При отправке результата AttemptService получает выбранные ответы, сопоставляет их с правильными значениями, рассчитывает балл и процент прохождения, после чего сохраняет попытку в базе данных.

Проектное разделение клиентского модуля реализовано через главное окно приложения, набор страниц для разных ролей и отдельный сетевой класс ApiClient. После авторизации приложение получает роль пользователя и формирует соответствующий набор разделов. Для студента отображаются страницы курсов, уроков, тестов, результатов и профиля. Для преподавателя доступны страницы управления курсами, конструктор курса, список студентов и аналитика. Для администратора предусмотрены разделы управления пользователями и просмотра системных данных.
Сетевой обмен вынесен из визуальных страниц в ApiClient. Этот класс формирует HTTP-запросы, добавляет заголовок авторизации, отправляет данные в формате JSON и преобразует ответы сервера во внутренние модели клиента. Благодаря этому страницы интерфейса работают с подготовленными объектами, а не с низкоуровневыми деталями HTTP-запросов.

В подразделе «Реализация базы данных и развёртывания»

Здесь нужно раскрыть физическую реализацию модели хранения, которую во второй главе лучше оставить на уровне связей сущностей:

Логическая модель данных, описанная во второй главе, реализована в PostgreSQL через набор связанных таблиц. Таблица users хранит пользователей и их роли, courses — учебные курсы и связь с преподавателем, enrollments — записи студентов на курсы. Таблицы lessons и materials описывают учебное содержание, а tables tests, questions и answers задают структуру тестирования. Таблица attempts хранит результаты прохождения тестов пользователями.
Для поддержания целостности данных используются первичные и внешние ключи, ограничения уникальности и правила каскадного удаления. Это позволяет избежать ситуаций, при которых материал остаётся без урока, вопрос — без теста, а результат прохождения — без пользователя или теста. Начальное создание схемы и демонстрационных данных выполняется через SQL-скрипт и используется при развёртывании контейнера PostgreSQL.
